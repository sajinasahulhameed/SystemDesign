# Functional Requirements in System Design

## What Are Functional Requirements?

Functional Requirements (FRs) define:

> **What the system should do.**

They describe the features, capabilities, and behaviours users expect from the system.

---

## Why Functional Requirements Matter

Saying:

```text
Build a chat application
```

is **not** a requirement.

It is only a vague idea.

Real requirements are specific.

Example:

- Users can send messages
- Users can create group chats
- Users can see delivery status
- Users can search messages

Each requirement affects architecture decisions.

---

# Architect Mindset

The architect's first responsibility is:

> Clarify requirements before designing anything.

Never assume requirements.

Always ask questions.

---

# Example: Chat Application

### Requirement

```text
Users can send messages
```

### Architect Questions

- Text only?
- Images?
- Videos?
- Documents?
- Maximum file size?
- Can messages be edited?
- Can messages be deleted?
- Do messages expire?

---

## Why It Matters

### Text Only

Simple architecture.

```text
User → Application → Database
```

---

### Video Support

Requires:

- Video storage
- CDN
- Video transcoding
- Streaming system

Architecture becomes much more complex.

---

# Technique: Start With User Stories

## User Story Formula

```text
As a <user>
I want to <action>
So that <benefit>
```

---

# Example: E-Commerce Platform

## User Types

### Buyers

Need to:

- Search products
- View product details
- Add to cart
- Make payment
- Track orders

---

### Sellers

Need to:

- List products
- Manage inventory
- View sales reports
- Process returns

---

### Administrators

Need to:

- Manage users
- Monitor transactions
- View analytics
- Handle disputes

---

## Key Lesson

Instead of saying:

```text
Build an e-commerce website
```

Break requirements down by:

- User type
- User actions
- Business goals

# Define Scope and Boundaries

A system can have hundreds of features.

Trying to build everything at once is a mistake.

---

Possible requirements:

- Upload videos

- Comments
- Likes

- Livestreams
- Monetisation

## MVP (Minimum Viable Product)

### Version 1

Must Have:

- Video upload
- Video playback

---

### Later Versions

Nice to Have:

- Monetisation

Prioritise:

```text

```

# Requirements Must Be Measurable

## Bad Requirement

```text
Users should upload videos quickly
```

Problem:

"Quickly" means different things to different people.

---

## Good Requirement

```text
Users should upload a 100 MB video
within 2 minutes on a broadband connection.
```

Specific.

Testable.

Measurable.

---

## Another Example

### Bad

```text
Search should be fast
```

### Good

```text
Search should return results
within 200 ms for 95% of requests.
```

---

## Why This Matters

Specific requirements drive design decisions.

Example:

Fast uploads may require:

- Multiple upload servers
- CDN
- Parallel uploads
- Resumable uploads

---

# Hidden Functional Requirements

Many projects fail because teams only discuss obvious features.

---

# Example: Social Media Platform

Everyone mentions:

- Posting
- Liking
- Commenting

---

But what about:

### Delete

- Can users delete posts?
- What happens to comments?

### Privacy

- Public accounts?
- Private accounts?
- Who can view content?

### Blocking

- What happens when User A blocks User B?

---

## Architect Rule

Ask:

> "What happens next?"

until all scenarios are understood.

---

# Edge Cases Become Requirements

Hidden scenarios often create redesigns later.

Good architects discover them early.

---

# Example: Ride-Sharing App (Uber)

## Obvious Requirements

- Request ride
- Accept ride
- GPS tracking
- Payment processing

---

## Hidden Requirements

### Driver Cancels Ride

What happens?

---

### Payment Fails

How do we recover payment?

---

### GPS Lost

How is tracking handled?

---

### Surge Pricing

How is pricing calculated?

---

### Scheduled Rides

Can users book in advance?

---

## Lesson

Every business scenario becomes a functional requirement.

---

# Functional Constraints

Some requirements include constraints.

These greatly affect architecture.

---

# Example: User Scale

Requirement:

```text
System supports
10 million active users
```

Implications:

- Load balancing
- Distributed systems
- Database sharding
- Horizontal scaling

---

# Example: End-to-End Encryption

Requirement:

```text
Messages must be end-to-end encrypted
```

Implications:

- No plaintext storage
- Key management
- More complex architecture
- Limited server-side search

---

## Key Lesson

Requirements are not just features.

Many requirements impose architectural constraints.

---

Requirements almost never stay the same.



### Version 3

```text

```

### Version 4


## Architect Goal

Design for growth.

Not over-engineering.

Not under-engineering.

Build systems that can evolve.

# Functional Requirement Checklist

Whenever gathering requirements ask:

### Users

- Who uses the system?

### Features

- What can each user do?

### Inputs

- What data enters the system?

### Outputs

- What should happen?

### Edge Cases

- What if something unexpected happens?

### Failure Cases

- What if a dependency fails?

### Constraints

- Scale?
- Security?
- Compliance?

### Future Growth

- What might be needed in 2 years?

---

# Common Mistakes

## Mistake 1

Starting design before understanding requirements.

---

## Mistake 2

Ignoring edge cases.

---

## Mistake 3

Ignoring delete/update scenarios.

---

## Mistake 4

Requirements are vague.

Example:

```text
Fast
Good
Easy
Quick
```

These are not measurable.

---

## Mistake 5

Trying to build every feature immediately.

No MVP.

---

# Architect Framework for Functional Requirements

For every requirement ask:

### What?

What should happen?

### Who?

Who uses it?

### When?

When can it occur?

### How?

How should it behave?

### What If?

What if something fails?

### Future?

Will this requirement grow?

# Exam Memory Trick

### Functional Requirements

> **WHAT the system does**

Examples:

- Send messages
- Upload videos
- Search products
- Create orders
- Make payments

### Non-Functional Requirements

> **HOW WELL the system does it**

Examples:

- Fast
- Scalable
- Reliable
- Secure
- Available
